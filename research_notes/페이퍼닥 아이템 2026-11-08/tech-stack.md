### 반드시 알아야 할 두 가지 함정

**(1) Presidio 한국 인식기의 체크섬은 2020년 10월 이전 발급분만 검증한다.**
소스 주석 그대로다: *"This validation is only for RRNs issued before October 2020. Therefore, it returns None, not False, at the end of the method."*
2020년 10월 이후 발급 주민번호는 뒤 6자리가 난수여서 체크섬이 없다. 즉 **체크섬만 믿으면 신규 발급분을 놓친다.** 정규식 패턴(신뢰도 0.5)으로만 잡히므로, 임계값을 낮게 두고 오탐을 감수하는 쪽이 옳다. 마스킹은 오탐 비용이 미탐 비용보다 싸다.

**(2) Presidio 한국 인식기의 CONTEXT 단어가 전부 영어다.**
`kr_rrn_recognizer.py`의 CONTEXT = `["Korean RRN", "Korean Resident Registration Number", "Resident Registration Number", "RRN", "rrn", "rrn#"]`.
한국 임대차계약서에는 **"주민등록번호", "주민번호", "생년월일"** 이 적혀 있다. Presidio 공식 문서도 *"different detection mechanisms such as regular expressions are language agnostic, the context words used to increase the PII detection confidence aren't"* 라고 명시한다. → **CONTEXT에 한국어 단어를 넣는 커스터마이징이 붙여넣기 수준으로 필요하다. 1시간 작업이고, 안 하면 신뢰도 점수가 안 올라간다.**

### 아키텍처 제약 — Next.js에 바로 안 붙는다

**한국어 PII 라이브러리는 JS/TS에 존재하지 않는다.** GitHub 저장소 검색(`korean pii language:typescript OR language:javascript`) 결과 **total_count = 0**. npm 레지스트리 검색(`korean pii masking`)도 한국어 전용 패키지를 반환하지 않았다(`hangul-toolkit`, `@pii-mask/core` 등 무관한 결과만).
→ 선택지는 둘뿐이다.
- **(a) Python 사이드카**: 마스킹 전용 Python 서비스를 따로 띄우고 Next.js가 호출. Supabase Edge Functions는 Deno라서 불가 — 별도 컨테이너(Fly.io/Cloud Run/온프레미스)가 필요하다. Vercel 안에 두면 **국내 리전 보장이 안 되므로 약점 #1을 못 푼다.**
- **(b) TS에 정규식+체크섬만 자체 포팅**: 주민번호·계좌·전화·이메일은 정규식으로 충분하다. 이름·비정형 주소는 포기. **가장 빠르고, 국외 전송 차단이라는 목표만 보면 이게 정답에 가깝다.**

### 약점 #3 룰 공백 4개 중 하나는 법령 확인이 선행된다

**주택임대차보호법 §3조의7(임대인의 정보 제시 의무)** — 조문 내용은 확인됐다. 임대인은 계약 체결 시 ① 해당 주택의 확정일자 부여일, ② 차임·보증금 등 정보를 임차인에게 제시해야 하고, **국세징수법·지방세징수법에 따른 납세증명서도 제시해야 한다.** 제3조의6 제4항에 따라 임대인이 사전 동의하면 이를 갈음할 수 있는 예외가 있다.
**단 시행일을 신뢰할 출처로 확인하지 못했다(미확인).** → 룰을 넣기 전에 법제처 OPEN API로 현행 조문과 시행일자를 직접 조회하라. 이게 위 API를 붙여야 하는 첫 번째 실무 이유다.
참고: 같은 맥락의 **공인중개사법 §25조의3(임대차 중개 시의 설명의무)** 도 룰 후보다.

### 버저닝 설계 권고 (약점 #2의 실질적 해법)

룰 엔진을 바꾸는 것보다 **스키마가 중요하다.** 지금 「v1.0 · 2026-06-10, 5개월째 개정 없음」이 문제로 보이는 이유는 룰셋 전체가 하나의 버전을 공유하기 때문이다. 룰 단위로 쪼개라.

```
rules          (id, 계약유형, 조항범주, 로직 JSONB, 근거법령_조문키, 중요도)
rule_versions  (rule_id, version, 유효_시작, 유효_종료, 변경사유, 변경자, diff)
law_snapshots  (조문키, 시행일자, 공포일자, 본문, 법제처_조회시각)
rule_law_link  (rule_id, 조문키, 마지막_대조시각, 대조결과)
```
법제처 API로 `law_snapshots`를 갱신하고 `rule_law_link.대조결과`가 깨진 룰만 사람이 본다. **그러면 "룰셋이 5개월 정지"가 "193개 중 N개가 법령 개정으로 검토 대기"라는 측정 가능한 숫자로 바뀐다.** 사업계획서에 쓸 수 있는 형태는 후자다.

## 7. LLM 보조 설계 (룰 정확도를 유지하면서)

학계·실무 모두 결론이 같다: **검증된 권위 출처에 대한 검색 + 결정론적 검증이 주된 완화책이고, 프롬프트와 선호학습은 덜 효과적이다.**

| 패턴 | 내용 | 페이퍼닥 적용 | 출처 |
|---|---|---|---|
| **인용 그라운딩 (citation grounding)** | LLM이 생성한 법령·판례 인용을 **실제 코퍼스의 인용 그래프에 대조**해 존재 여부를 검증. 한 2026 연구는 우크라이나 판결 1억 80만 건으로 그래프를 만들어 대조했고, **생성 인용의 13~21%가 환각**이었다고 보고. 법조문 추출 단계는 **컴파일된 정규식으로 검증 표본 정밀도 100%** | **페이퍼닥은 이 코퍼스를 이미 가질 수 있다** — 법제처 `조항호목` API가 바로 그 권위 출처다. LLM이 「주택임대차보호법 제7조의2」를 말하면 API로 존재·본문을 확인한 뒤에만 리포트에 넣는다 | https://arxiv.org/pdf/2606.00898 |
| **환각 3분류** | 환각을 **① 존재(existence) ② 문맥 적합성(contextual relevance) ③ 시간적 유효성(temporal validity)** 로 분해. 폐지·개정된 조문은 "존재"하지만 틀린 근거다 | **③이 페이퍼닥의 급소다.** 룰셋이 5개월 멈춘 상태에서 LLM이 구 조문을 인용하면 "존재 검증"은 통과한다. `law_snapshots.시행일자`로 시간 검증을 별도 게이트로 둬라 | 위와 동일 |
| **참조 단위 감사(reference-level audit)** | 초안 답변을 감사해 **참조별 상태 목록 + 참조가 권위출처에 링크된 마크업 답변**을 반환 | 리포트의 모든 「근거 법령」에 ✅/⚠/❌ 상태를 달아 출력. **검증 실패한 근거는 리포트에서 빼지 말고 "확인 불가"로 표시**하는 쪽이 신뢰에 유리하다 | https://aclanthology.org/2026.propor-2.9.pdf |
| **원자 주장 분해 + 기호적 검증** | 출력을 원자 단위 주장으로 쪼개 각각 코퍼스 대조. 더해 **조문번호 형식 정규식 검증** 같은 기호적 체크를 붙인다 | 「이 문장이 불리하다」와 「근거는 §X」를 분리된 주장으로 취급. 후자는 결정론적으로 검증 가능하다 | 실무 블로그 — 증거가 아닌 지침으로 취급 |
| **프롬프트만으로는 안 된다** | 한 법률 인용 벤치마크: **명시적 기권(abstention) 지시는 자신만만한 조작은 줄이지만 인용 정확도는 개선하지 않았다.** 최상위 모델도 인용 검색·완성 점수가 낮았다 | "모르면 모른다고 해"로 때우려는 설계를 버려라. 외부 그라운딩이 필수다 | LegalCiteBench: https://arxiv.org/pdf/2605.10186 |

```
계약서 텍스트
  ↓ (1) 조항 분리  ← LLM (구조화 출력. JSON 스키마 강제)
  ↓ (2) 불리 판정  ← 룰셋 193개 (결정론적. LLM 미개입)
  ↓ (3) 근거 법령  ← 룰에 하드코딩된 조문키 → 법제처 API로 본문·시행일 조회
  ↓ (4) 설명 문장  ← LLM (근거 본문을 컨텍스트로 받아 재작성만. 새 법령 인용 금지)
  ↓ (5) 검증 게이트 ← LLM 출력에 룰셋에 없는 조문키가 등장하면 차단
```
**핵심은 (5)다.** LLM이 인용할 수 있는 조문 집합을 룰셋이 보유한 조문키로 **화이트리스트 제한**하면, 법률 도메인 환각의 치명적 경로가 구조적으로 닫힌다. 이건 모델 성능과 무관하게 작동한다.
**교차검증 용도**로는 반대 방향도 쓸 수 있다: LLM에게 독립적으로 불리 조항을 찾게 하고, **룰셋이 못 잡은 것만 모아 룰 공백 후보 큐로 보낸다.** 사용자에게 보여주는 판정에는 넣지 않는다. 이게 약점 #3(룰 공백 4개)을 지속적으로 메우는 저비용 장치다.

## 8. 평가/벤치마크 (약점 #5 — 품질을 증명할 방법이 없다)

**한국어 임대차계약 불리조항 판정용 공개 평가셋은 못 찾았다.** 쓸 수 있는 것은 영어 CUAD·UNFAIR-ToS(§3), 한국 법률 일반 능력 벤치마크 LBox Open·KCL·KBL(§4)뿐이고, **KCL은 비상업 라이선스라 상용 품질 측정에 쓸 수 없다.** 따라서 자체 평가셋이 불가피하다.

### 자체 평가셋 최소 설계 (가장 싼 버전)

**이 절은 조사 결과가 아니라 제안이다.** 근거는 §7의 인용 그라운딩·3분류 문헌과 CLAUDETTE가 "작은 학습셋으로 80% 수준을 냈다"는 보고다.

1. **규모: 계약유형 6종 × 20건 = 120건.** CLAUDETTE가 상대적으로 작은 데이터로 재현율 80%대를 보고했다. 120건이면 193개 룰 중 자주 발동하는 상위 룰의 정밀도는 측정된다. **전수 측정은 포기하고 "상위 N개 룰의 정밀도"를 측정 대상으로 선언하라.**
2. **라벨: 조항 단위 3분류.** `불리 / 중립 / 임차인에게 유리`. 여기에 **근거 조문키**를 함께 라벨링한다. 판정이 맞아도 근거가 틀리면 제품이 틀린 것이다 — 이 둘을 분리해서 재는 게 핵심이다.
3. **4개 지표만 본다.**
   - 조항 분리 경계 정확도 (조항을 제대로 쪼갰는가)
   - 불리 판정 정밀도 / 재현율 (**오탐이 더 비싸다** — 겁주는 리포트는 신뢰를 잃는다)
   - **근거 조문 정확도** (판정이 맞을 때, 인용한 조문이 실제로 그 근거인가)
   - **근거 시간 유효성** (인용 조문이 계약 체결일 기준 현행인가) ← 룰셋 정지 문제를 직접 재는 지표
4. **적대 샘플을 섞는다.** 표준계약서 그대로인 건(= 불리 0건이어야 함)을 20% 넣어 **오탐률을 따로 측정**한다. 이게 없으면 "다 불리하다고 말하는 모델"이 재현율 100%로 보인다.
5. **시드 확보**: 공정거래위원회 표준임대차계약서, 주택임대차보호법 조문(법제처 API), 법제처 「법령해석례」·「행정심판례」가 "무엇이 불리한가"의 공적 근거다. **AI허브 법률 데이터는 라이선스 확인 전까지 보류.**
6. **회귀 테스트로 운영**: 룰을 고칠 때마다 120건을 재실행하고 **룰 버전별 점수를 `rule_versions`에 기록.** 그러면 "193개 룰, v1.2, 상위 40개 룰 정밀도 0.89, 근거 조문 정확도 0.94" 같은 문장이 사업계획서에 들어간다. **지금은 이 문장이 없는 것이 문제다.**
7. **개인정보 주의**: 실계약서를 평가셋에 넣으려면 §1 마스킹을 먼저 통과시켜라. ko-pii README도 *"테스트·버그 보고에 실제 개인정보를 넣지 마라"* 고 경고한다.

## 지금 당장 붙일 것 3개

### 1. Presidio 한국 인식기 + Tesseract `kor` 를 OCR 앞단에 — **약점 #1**
`presidio-analyzer`의 `KrRrnRecognizer`가 **이미 코드에 존재하고 MIT이며 저장소는 조사일 당일에도 커밋이 있다.** 쓸 수 있는 물건이 이미 있으니 만들 게 아니라 붙이면 된다.
단 **두 가지를 반드시 고쳐야 한다**: CONTEXT에 "주민등록번호·주민번호"를 넣을 것(현재 영어뿐), 그리고 체크섬을 통과 조건으로 쓰지 말 것(2020년 10월 이후 발급분은 체크섬이 없다). **급하면 (b)안 — 주민번호·계좌·전화 정규식만 TS로 포팅 — 이 더 빠르고, 국외 전송 차단이라는 목표만 보면 충분하다.**

### 2. 법제처 국가법령정보 OPEN API + 룰 단위 버저닝 스키마 — **약점 #2, #3**
`조항호목` 단위 조회와 `법령 변경이력`이 공식 제공 범주로 확인됐다. 193개 룰에 조문키를 달고 매일 대조하면, **"5개월째 개정 없음"이 "193개 중 N개 검토 대기"라는 측정값으로 바뀐다.** 룰 공백 #1(§3조의7)의 시행일조차 지금 신뢰할 출처로 확인이 안 되는 상태 — 이 API가 그걸 바로 해결한다.
요금·약관이 안내 페이지에 없으므로 **02-2109-6446으로 상업적 이용 가능 여부를 먼저 확인하라.** 이게 확인되지 않으면 나머지 설계가 무의미하다.

### 3. 자체 평가셋 120건 + 근거 조문 정확도 지표 — **약점 #5, #4**
한국어 임대차 불리조항 공개 평가셋은 **존재하지 않고**, 유일한 한국 법률 벤치마크 후속작(KCL)은 **비상업 라이선스로 막혀 있다.** 외부에서 가져올 수 없으니 만드는 것 외에 길이 없다.
120건은 룰셋 전체를 증명하진 못하지만, **「상위 40개 룰 정밀도 + 근거 조문 정확도 + 오탐률」이라는 세 숫자를 만들어낸다.** 계약유형별로 20건씩 고정하면 **전세 룰이 25개뿐이라는 배분 문제(약점 #4)가 어느 룰이 비어 있는지로 드러난다** — 지금은 개수만 알고 무엇이 비었는지 모른다.

## 못 찾은 것

1. **등기부 API** — 법원행정처/인터넷등기소의 공개 API를 확인하지 못했다. 더구나 `www.iros.go.kr/robots.txt`가 `Disallow: /`로 전면 차단해 크롤링 경로도 막혀 있다. 민간 유료 중계가 유일한 경로로 보인다.
2. **국세·지방세 체납 정보 API** — 개인 체납 사실은 성질상 공개 API가 될 수 없다. 룰 공백 #2(당해세 우선변제)는 **데이터가 아니라 계약서 텍스트 점검 룰**로 설계해야 한다.
3. **한국어 계약서 불리조항 탐지 오픈소스** — GitHub·논문 모두 공백. 영어 전용(CUAD/CLAUDETTE/UNFAIR-ToS)만 존재한다. **페이퍼닥 룰셋의 대체재가 없다는 뜻이고, 이건 차별점 근거로 쓸 수 있는 사실이다.**
4. **조항 분리(clause segmentation) 전용 오픈소스·데이터셋** — 권위 있는 것을 확인하지 못했다.
5. **JS/TS 한국어 PII 라이브러리** — GitHub 저장소 검색 total_count 0, npm 검색도 해당 없음. Next.js 안에서 끝낼 방법이 없다는 뜻이다.
6. **계약서의 표·도장(인감) 혼재 문서에 대한 OCR 공식 벤치마크** — 표 인식 지원은 surya/PaddleOCR 계열에서 확인했으나 **도장 처리 언급은 어디서도 확인하지 못했다.**
7. **법제처 OPEN API의 요금·공식 이용약관 전문** — 안내 페이지에 명시되어 있지 않다. 전화 문의 필요(02-2109-6446).
8. **AI허브 법률 데이터셋의 상업적 이용 가능 여부** — 공식 약관을 확인하지 못했다.
9. **LBox Open의 라이선스** — 논문 미러에 CC BY-NC-SA 4.0 표기가 있으나 공식 저장소에서 확인하지 못했다.
10. **Upstage Document Parse의 데이터 처리 리전과 공식 가격표** — 제3자 자료만 확인됐다.
11. **CLOVA OCR의 물리적 데이터 저장·처리 위치** — 리전(KR-1/KR-2) 선택은 확인했으나, 그것이 개인정보 처리 위치를 어떻게 규정하는지는 확인하지 못했다. 국외이전 쟁점이라면 개인정보 처리방침·계약서로 확인해야 한다.
12. **Durable Rules** — 저장소 상태를 확인하지 못했다.
13. **Supabase에서의 pgaudit 운용과 업로드 안티바이러스 연동 공식 문서** — 확인하지 못했다.
14. **주택임대차보호법 §3조의7의 시행일** — 조문 내용은 확인했으나 시행일을 신뢰할 출처로 확인하지 못했다. 법제처 API로 직접 확인할 사항.
