## 명제

**지금 가장 먼저 할 일은 2주 안에 실사용자를 만드는 것이다. 이 제품은 아직 아무도 써본 적이 없고, 그 사실이 다른 모든 문제보다 앞선다.**

정확히 말하면: **낯선 사람 100명을 모으는 일이 아니다.** 계약을 앞둔 사람 **16명**에게 라이브 제품 링크를 쥐여주고, **본인이 직접 로그인해 리포트를 끝까지 보게 한 뒤**, 그 리포트가 계약 내용을 바꾸는지 **센다**. 소스·배포 권한·결제 구현·약관 수정 **어느 것도 필요 없다** — 제품은 **지금 이 순간 완성된 상태로 열려 있다**(`hasAccess = !!user`). 그래서 이것만이 이번 주에 의뢰인 혼자 착수할 수 있는 유일한 작업이다.

## 변론 — 근거 5개

### 근거 1. 「제품이 별로다」는 측정된 적이 없다. 데이터가 그 말을 지지하지 않는다 (계산 가능)

최근 64일간 부동산·계약 글 온사이트 조회 **합계 30회**, 페이퍼닥 클릭 0 (`traction.md` 메인 제공 전제). 이 30뷰/0클릭으로 말할 수 있는 것은 다음뿐이다.

| 참 CTR 가정 | 30뷰에서 클릭 0이 나올 확률 |
|---|---|
| 2% | **54.5%** |
| 3% | 40.1% |
| 5% | 21.5% |
| 10% | 4.2% |

**0/30 의 CTR 95% 상한은 9.5%다.** 즉 이 데이터는 「CTR 0%」와 「CTR 9%」를 구분하지 못한다. 평범한 CTR 2%였어도 클릭 0이 나올 확률이 **절반을 넘는다**. 이건 나쁜 결과가 아니라 **결과가 아니다**.

누적 분석 110건도 같다. `counter-index.md` 가 확인한 대로 카운터는 고장이 아니라 Supabase RPC `analyses_stats` 실호출값(`total:110`, 월세 89)이고, 그중 다수가 의뢰인 본인 테스트일 가능성이 높다(동 문서 추정 85%). 그러면 17개월간 이 제품을 통과한 **실제 타인의 계약서는 한 자리 수**다. 블로그 8,244 조회 중 진짜 클릭 1건도 같은 성질이다 — 그 8,244은 타깃 글이 아니었다.

**그리고 이제 마지막 변명까지 사라졌다.** 번들 확인 결과 `hasAccess = !!user` — **이 제품은 17개월간 단 한 번도 유료 벽에 막혀 있지 않았다.** 구글 계정만 있으면 누구나 무제한으로 분석을 돌릴 수 있었고, 크레딧 잔액은 `localStorage` 에서만 읽혀 접근 판정에 들어가지도 않는다. 그런데 누적 110건이다.

그러므로 「결제가 막아서 안 쓴 것」·「관계자 제한이 걸려서 못 쓴 것」이라는 설명은 **코드 수준에서 불가능하다.** 남는 설명은 두 개뿐이다.
- (a) **아무도 이 사이트를 본 적이 없다** — 타깃 노출 64일 30회, `site:` 색인 흔적 0건, 외부 링크 0 (`counter-index.md`)
- (b) 봤는데 원하지 않았다 — 이걸 주장하려면 노출 데이터가 필요한데, 그게 30회다

**(a)가 남는다.** 실패의 원인은 제품도 가격도 약관도 아니고 **노출**이다. 그리고 노출은 소스 권한 없이 이번 주에 만들 수 있는 유일한 것이다.

**결론: 「좋다」도 「나쁘다」도 증명된 적이 없다. 한 번도 시험대에 오르지 않았다.** 시험대에 올리는 비용이 2주라면, 다른 어떤 작업보다 먼저다.

### 근거 2. 다른 모든 작업의 가치가 이 측정의 결과에 **조건부**다 — 순서가 거꾸로다

| 작업 | 사용자 0일 때 산출물 | 수요 확인 후 산출물 |
|---|---|---|
| 결제 개시(약관 2곳 수정 + PG 심사 10~14영업일 + 대표 서명, `payment-path.md`) | **매출 0원.** 0명 × 가격 = 0 | 가격·전환율이 붙은 매출 추정 |
| ↳ **번들 확인으로 더 길어졌다** | 크레딧이 `localStorage` 에서만 읽히고 `hasAccess` 는 잔액을 보지 않는다 → **결제는 UI 껍데기이고 서버 측 권한 시스템이 구현된 적이 없다.** 즉 B 경로는 "약관 2곳 + PG 심사"가 아니라 **서버 엔타이틀먼트 신규 개발**을 포함한다 → 소스 권한 **필수** | 동일 |
| 소스·Vercel 권한 확보 | 아무도 안 보는 랜딩을 고칠 권리 | 어디를 고칠지 아는 상태 + 요청 근거 |
| IP·분사 협상 | **가치 미상 자산**을 달라는 요구 | 「내가 만든 수요」를 들고 하는 협상 |
| P0 4건 수정 (샘플·히어로·카카오로그인·모바일) | 유입 0에 곱하는 개선 | 16명이 어디서 막혔는지 아는 상태 (P0-3 이탈자 수 포함) |
| 토스 미니앱 | 부동산 카테고리 제한 미확정 + CSR 재개발 | 동일 (이건 어차피 뒤다) |

결제를 여는 일은 **고객이 생기는 즉시 가치가 생기지만, 고객 없이 열면 그냥 0이다.** 반대로 수요 측정은 결제가 열려 있지 않아도 지금 할 수 있다. **지금 할 수 있고 나중에도 가치가 유지되는 작업 vs. 지금 해도 0이고 나중에 해도 똑같이 걸리는 작업** — 전자가 먼저다.

**번들 발견은 이 비대칭을 더 벌렸다.** 반대편 경로(결제 우선)는 서버 권한 시스템 신규 개발이 추가되어 **소스 권한 의존이 더 깊어졌다** — 그리고 소스 권한은 두 달간 확보되지 않았다. 내 경로는 반대로 **요구사항이 하나 줄었다**: 컨시어지 대행이 더는 필요 없고, 사용자가 제품을 직접 끝까지 쓴다. 같은 사실 하나가 두 명제에 반대 방향으로 작용했다.

### 근거 4. 「제품 완성도」와 「제품 적합성」을 혼동하고 있다 — 193개 룰셋은 한 번도 채점되지 않았다

이것은 전부 **표면** 지표다. 한 번도 측정되지 않은 것은 룰셋의 **정밀도**다:
- 실제 계약서 1건에 193개 중 **몇 개가 발화**하는가
- 발화한 것 중 **사용자가 "그건 상관없어요"** 라고 말하는 비율(= 오탐)

### 근거 5. 반대편 작업들은 **두 달간 실제로 실패했다.** 이 작업만 의뢰인 통제 범위 안에 있다

2026-09-08 감사가 P0로 찍은 4건(샘플 없음·이미지 히어로·구글 단독 로그인·모바일 깨짐)이 **2026-11-07 현재 4/4 미수정**이다. P1 4건도 3건 미수정·1건 부분(투어 24시간 스누즈). 그런데 그 사이 **재배포는 있었다** — 2026-11-03~11-05, 정적 자산 `Last-Modified: 2026-11-05 01:16 GMT` (`deploy-state.md`, 추정 75%).

이 두 사실의 결합이 결정적이다. **배포 파이프라인은 살아 있고, 제품 내용은 변하지 않았다.** 누군가 빌드를 돌릴 수 있는데 의뢰인이 지적한 것은 하나도 안 고쳐졌다. 접근 권한이 없거나, 협조가 없거나, 둘 다다.

**따라서 「제품을 먼저 고친다」로 시작하는 계획은 이미 두 달간 집행 실패를 기록했다.** 같은 전제를 세 번째로 시도하는 것이 여섯 번째 유입 시도보다 나을 이유가 없다. 제품을 **있는 그대로 쓰는** 계획만이 첫 단계가 의뢰인 자신의 손 안에 있다 — 그리고 번들 확인으로 드러난 대로, **있는 그대로의 제품은 이미 완성 상태로 열려 있다.** 고칠 필요가 없는 것을 고치려고 두 달을 썼다.

반대로 묻는다. **소스 권한을 먼저 받는 계획은 이번 주에 무엇을 집행하나?** `deploy-state.md`·`payment-path.md` 가 낸 1순위 작업은 전부 "의뢰인이 대표에게 연락 → 대기"다. 대기 중에 할 일이 필요하고, 그게 이것이다. **두 작업은 배타적이지 않다.** 대표 연락은 1시간이고, 나머지 13일은 비어 있다.

### 반론 2. 「약관 제3조가 분석을 관계자에게만 제공한다고 못박았다. 낯선 사람 100명을 데려와도 리포트를 못 본다」

**이 반론은 사실이 아니다. 코드 수준에서 깨졌다.**

메인이 라이브 번들에서 떼어낸 `useCredits` 훅(`123-6efa373e817f0fdc.js`, `app/layout-5fa01c9e6e17ee8a.js` — 분석용 `pd_credits` / 진단용 `pd_diag_credits` 두 벌):

```js
const unlimited = !!user;                                  // 로그인했으면 무조건 true
useEffect(() => {                                          // 잔액은 localStorage 에서만
  const v = localStorage.getItem("pd_credits"); ...
}, []);
return { balance, isAdmin, unlimited, hasAccess: unlimited };   // balance 를 보지 않는다
```

세 가지가 확정된다.
1. **`hasAccess = !!user`.** 구글 로그인 하나로 **누구나 무제한** 분석. 관계자 명단 조회도, 크레딧 차감도 접근 판정에 없다.
2. **서버 검증이 없다.** 잔액이 `localStorage` 에만 있고 접근은 그걸 보지도 않는다 → 결제는 구현된 적이 없다.
3. **가격은 이미 정해져 있다**: 분석 1건 3,900 / 3건 9,200 / 10건 22,600, 진단 1건 2,900 / 3건 6,900 / 10건 16,900.

**따라서 「받을 수 있는 건 무료 체크리스트뿐」은 틀렸다. 완성된 193룰 리포트가 지금 로그인한 누구에게나 열려 있다.** 컨시어지 대행은 불필요해졌고, 검증은 **대리 측정이 아니라 실제 제품 퍼널**을 재게 된다. 반론이 내 설계를 **강화**했다.

**남는 실제 장애물은 하나로 줄었다 — 구글 단독 로그인(P0-3).** 그리고 이건 이제 변명이 아니라 **측정 대상**이다. 링크를 받은 16명 중 몇 명이 로그인을 통과해 리포트에 도달하는가 = Gate 2. 통과율이 낮으면 **"P0-3을 고쳐야 한다"가 숫자가 붙은 요구로 바뀐다**(현재는 두 달째 근거 없는 요구다). 샘플 없음(P0-1)·이미지 히어로(P0-2)도 같다 — 링크를 손으로 쥐여주는 경로에서는 랜딩을 거치지 않으므로 측정을 막지 못한다.

### 반론 2에서 **새로 생긴 긴장** (내 명제에 불리한 쪽)

약관은 "관계자에게만"이라 **공표**해 두고 코드는 전원 개방이다. 이 간극으로 불특정 다수를 끌어오는 것은 중립적 행위가 아니다. 내가 **인정하는 위험** 셋:
1. 공표와 동작이 어긋난 상태에서 사용자가 리포트를 신뢰해 손해가 나면, 회사는 "열어두지 않았다고 공표한 서비스"에서 책임 노출을 진다.
2. 의뢰인은 **재직자이고 대표가 아니다.** 코드가 열려 있다는 사실이 의뢰인에게 **권한을 주지는 않는다.** 오히려 "열려 있는 줄 알았다"는 변명이 불가능해져 **서면 허락의 필요가 커졌다.**
3. 약관 제8조(불리한 개정 30일 전 공지)와의 관계, 그리고 "이 구멍을 알고도 썼다"는 사후 평가 — 전부 내 판단 범위 밖이다.

**이 세 가지는 `legal-ip.md`(미작성)에 맡긴다. 나는 "코드상 열려 있다"는 사실만 전제로 쓴다.** 그리고 그래서 설계의 Day 0 요청이 더 중요해졌다 — **대표에게 「무료 베타 16명, 로그인 접근으로」 서면 허락을 받는 것.** 이 요청은 쟁점을 소멸시키는 동시에, 소스·IP·PG 서명이라는 큰 요구를 쓰기 **전에** 상대가 협조하는 사람인지 1~2일에 알려준다. **싼 탐침을 먼저 쏘는 것이 순서다.** (「틀릴 조건 2」로 걸어 둔다.)

부수로 적어 둔다(내 명제와 무관, 의뢰인이 알아야 할 사실): 10건 묶음(22,600원)은 계약서 검토가 **1회성 수요**(`traction.md`)라는 사실과 어긋난다. 가격표가 존재하지 않는 반복 사용을 가정하고 있다.

### 반론 3. 「IP가 회사에 귀속한다고 약관에 공표돼 있다. 지금 사용자를 만들면 남의 자산 가치만 올려주는 것 아닌가」

세 가지로 답한다.

**(a) 이 검증이 만드는 자산은 약관 제6조의2가 열거한 목록에 **없다**.**
조항이 귀속시킨 것: "소프트웨어·검수 룰셋·분석 로직·화면 디자인·상표·문서". 이 검증이 만드는 것: **계약 직전인 사람 16명이 누구이고 어떤 말로 문제를 설명하며 리포트의 어느 줄에서 손을 멈추고 무엇에 돈을 낼 의사가 있는지에 대한 1차 지식.** 이건 소프트웨어도 룰셋도 로직도 디자인도 상표도 문서도 아니다. 의뢰인의 머리와 노트에 남고, 분사가 깨지든 성사되든 **들고 나갈 수 있는 유일한 자산**이다. 지금 이 사안에서 명확히 의뢰인 소유라고 말할 수 있는 것은 이것뿐이다.

**(b) 수요 증거 없이는 협상에 가격이 없다.** 지금 분사·IP 이관을 요구하면, 의뢰인은 **가치가 확인되지 않은 자산**을 달라고 하는 것이다. 대표가 "얼마치인데?" 라고 물으면 답이 없다. 2주 뒤에는 둘 중 하나가 된다 — (i) 수요 확인 → "내가 만든 것"을 근거로 협상, (ii) 수요 부정 → **이기지 않아도 되는 협상을 아껴서 관계 자본을 쓰지 않음**. **두 결과 모두 지금 눈 감고 협상하는 것보다 낫다.**

**(c) 룰셋이라는 모트는 이미 회사가 스스로 공개했다.** `/methodology` 가 193개 점검항목 + 근거 법령을 **전량 공개**하고 있고(269KB, `deploy-state.md`), 내용의 출처는 국토부 표준계약서와 법령 — 공개 자료다. 편집저작물로서의 권리는 남을 수 있으나(법무 판단 영역, 신뢰도 낮음), **이 193줄이 모방을 막는 역할은 이미 포기된 상태**다. 경쟁사 부메랑은 이미 ₩3,300/30일로 결제를 받고 있다(`_BRIEF.md` 전제 8). 그러므로 지킬 가치가 남아 있는 것은 룰셋이 아니라 **유통과 사용자**이고, 그 둘은 아직 존재하지 않는다. **아직 존재하지 않는 것을 누가 소유하느냐를 두고 다투는 것이 지금의 상태다.**

### 반론 4. 「다섯 번 실패했다. 뭉게 269편·네이버 63편·배너 3채널·SEO 28URL — 전부 유입 0. 여섯 번째가 다를 이유는?」

**다섯 번이 전부 같은 한 가지였기 때문이다.** 네 시도의 공통 구조:

| 시도 | 구조 | 결과 |
|---|---|---|
| 뭉게 블로그 269편 | 내 도메인에 글을 쌓아 검색에서 발견되기를 기다림 | 색인 29/1,041(2.8%), GSC 2개월 노출 168·클릭 2 |
| 네이버 블로그 63편 | 동일 | 유입 0 |
| 배너 3채널 | 내 글 읽는 사람에게 배너 노출 | 타깃글 조회 64일 30회 |
| 자체 SEO 28 URL | 내 도메인 페이지를 더 만듦 | `site:` 색인 흔적 0건 (`counter-index.md`) |

**네 개 전부 "모르는 사람이 검색해서 내게 오기를 기다리는" 풀(pull) 방식**이고, 제품 정의어의 월 검색량이 **10회**(`전세계약서검토`)인 시장에서 이 방식은 **구조적으로** 작동할 수 없다. 색인조차 됐다면 최대 10명이 왔을 것이다. 실패의 원인은 집행량이 아니라 **방향**이었다 — 332편을 쓴 사람이 성실하지 않아서가 아니다.

여섯 번째가 다른 점은 **종류**다:

| | 1~5차 | 6차(제안) |
|---|---|---|
| 방향 | pull — 검색 기다림 | **push — 아는 사람에게 직접** |
| 대상 | 익명 다수 | **계약서를 손에 든 지명된 개인** |
| 시점 | 불특정 | **서명 직전 (수요가 존재하는 유일한 수일)** |
| n | 8,244 노출 / 1 클릭 | **16명 전수 추적 (로그인·분석·수정요구 단계별)** |
| 전달 | 익명 링크 노출 → 클릭 기다림 | **지명된 개인에게 1:1 링크 전달 (클릭 확률 단계 삭제)** |
| 필요 권한 | 도메인 권위 | **없음** (제품은 이미 개방 — 대표 서면 허락 1건만) |
| 실패 시 알게 되는 것 | 아무것도 (노출 30회) | **어느 단계에서 죽는지** — 공급 / 로그인 통과 / 행동 변화 중 하나로 확정 |

그리고 결정적으로, 5차까지는 **실패해도 아무것도 배우지 못하는 설계**였다. 30뷰에서 0클릭은 정보가 아니다(근거 1). 6차는 **실패하면 제품을 포기할 근거가 나온다.** 그게 여섯 번째를 돌릴 유일한 정당한 이유다.

## 2주 검증 설계

**이름: 실제품 셀프서비스 검증 16건**
**집행자: 의뢰인 1인. 총 15시간 / 14일 (≈ 1.1시간/일).**
**필요 권한: 없음.** 제품은 이미 완성 상태로 열려 있다(`hasAccess = !!user`). 필요한 것은 링크 1개 + 휴대폰 + 스프레드시트.

> **컨시어지 설계를 폐기하고 셀프서비스로 바꿨다.** 사용자가 직접 로그인해 직접 돌리므로 (a) 건당 의뢰인 시간이 45분 → 약 20분으로 줄어 **n 을 12 → 16 으로 올릴 수 있고** (b) 대리 측정이 아니라 **실제 제품 퍼널**(로그인 → OCR 입력 → 리포트)을 재며 (c) 로그인 마찰이라는 진짜 장애물이 측정 대상 안에 들어온다. 묶음 제약이 풀려서 설계가 더 좋아졌다.

### 사전 (Day 0, 1.5시간)
| | 작업 | 산출물 |
|---|---|---|
| 0-a | 대표(신해민)에게 **서면 요청**: "분사 전 수요 검증용으로 지인 16명에게 로그인 접근으로 분석을 무료 이용하게 해도 되겠습니까. 약관은 관계자 한정으로 적혀 있으나 코드상 로그인 전원 개방이라 확인이 필요합니다" | 서면 OK (또는 거절 — 그 자체가 결론) |
| 0-b | 로컬 스프레드시트: 16행 × `유입경로 / 계약유형 / 링크전달일 / 로그인완료 Y·N / 분석완료 Y·N / 발화룰수 / 사용자가 유효하다고 한 룰수 / 수정요구 Y·N / 수정요구 항목 / 지불의사(0·3,900·9,200) / 추천발생 Y·N / 막힌 지점` | 측정 장부 |
| 0-c | 본인 계정으로 1회 전수 리허설 — 로그인부터 리포트까지 **몇 분 걸리는지, 어디가 걸리는지** 기록 | 기준선 1줄 |

> 0-a의 문구에 **약관-코드 간극을 명시**한다. 숨기고 진행하면 나중에 의뢰인이 그 구멍을 알고 이용했다는 평가를 받는다. 1시간짜리 요청이고 13일을 기다리지 않는다.

### Gate 1 — 공급 (Day 1~4, 4시간): 계약을 앞둔 사람을 **찾을 수 있는가**
싼 순서로, 커뮤니티 글쓰기·가입 없이:
1. **1~2차 인맥 레퍼럴** (주력). 지인 15명에게 1:1로 "전·월세 계약하거나 갱신하는 사람 있으면 연결해줘, 193개 항목으로 무료 점검 링크 줄게". 브로드캐스트 아님. 의뢰인은 1994년생 서울 — 또래가 임대차 계약 최빈 코호트다.
2. **지식iN 답변 후 개별 제안** (보조, `traction.md` 선택 채널). 질문에 **먼저 실제로 답한 뒤** 링크 제안. 의뢰인이 운영원칙을 먼저 읽는다(`traction.md` #1, 0.5h). 링크 금지면 쪽지·프로필 경로로 대체.
3. 그 외 전부 버린다 — 피터팬·디시·중개사·지자체·광고 (`traction.md` 판정 그대로).

**Gate 1 측정값: Day 4까지 "해보겠다"고 하고 링크를 받은 사람 수.**

### Gate 2 — 통과 (Day 1~14, 3시간): 사람들이 **제품을 통과하는가** ← 새로 측정 가능해진 것
링크 전달 후 손을 대지 않는다. 48시간 뒤 1회만 확인(1인 약 10분).
- **로그인 완료 / 분석 완료** 를 센다. 완료 못 한 사람에게는 **어디서 멈췄는지 한 문장**만 받는다
- 구글 계정이 없거나 거부한 사람은 **별도 집계** (P0-3의 직접 비용)
- 그중 **5~6명은 관찰 모드**: 통화·화면공유로 옆에서 보며 멈추는 지점을 기록한다 (약 50분/명, 5시간). 셀프서비스 실패는 **조용해서** 이유를 모르기 때문에 이 팔이 반드시 필요하다

**Gate 2 측정값: 링크를 받은 16명 중 로그인+분석을 완료해 리포트에 도달한 사람 수.**

### Gate 3 — 가치 (Day 4~14, 4.5시간): 리포트가 **행동을 바꾸는가**
리포트에 도달한 사람에게만, 1인 약 20분:
1. **발화 룰 수** 와 **"이건 상관없다"고 말한 룰 수**(= 오탐) 기록
2. 실제 가격으로 묻는다: **"다음 계약 때 3,900원이면 쓰시겠어요? 3건 9,200원은요?"** (번들에 박힌 실가격)
3. **3일 뒤 1회 확인**: "집주인·중개사에게 수정 요구하셨어요? 어떻게 됐어요?"
4. 추천이 발생했는지 기록 (요청하지 않는다 — 자발만 센다)

**Gate 3 1차 측정값: 리포트를 근거로 계약 내용 수정을 요구한 사람 수.**
이걸 1차로 쓰는 이유: 설문 지불의사는 싼 신호라 믿을 수 없고, **집주인에게 전화해 조항을 바꾸자고 말하는 것은 비용이 드는 행동**이며 리포트가 현실을 바꿨다는 유일한 직접 증거다.

### 부수 산출물 (이 설계가 공짜로 주는 것)
- **룰셋 정밀도 첫 측정치**: 발화 룰 대비 사용자 인정 비율. 193개 중 무엇이 실제로 쓰이는지, 갭 4건 중 무엇이 먼저인지가 처음으로 데이터가 된다 (근거 4)
- **P0-3 의 가격표**: 구글 로그인에서 몇 명이 떨어졌는가 → 두 달째 근거 없던 "카카오 로그인 추가" 요구에 숫자가 붙는다
- **분사 협상 자료**: 수요가 확인되면 테이블에 올릴 유일한 숫자
- **대표 협조 여부 + 약관-코드 간극 처리 방침**: 0-a 응답으로 1~2일 내 확인

| **3명 이하** | **실패(부분 패배)** | 참 통과율 50%라면 이 결과 확률 **1.06%** | **제품의 현관이 사용자를 죽인다**가 확정. Gate 3 은 n 부족으로 판정 불가. 이 경우 **다음 작업은 유입이 아니라 소스 권한 + P0-3·P0-1 수정**이고, **반대편이 옳아진다 — 단 숫자가 붙은 상태로** |

### Gate 3 — Day 14 (수정 요구 건수)
임계값은 **양쪽 오류율 2% 이하** 지점으로 잡았다. Gate 1 결과에 따라 열을 고른다:

| 수정 요구 | 판정 | n=16 일 때 | n=10 일 때 | 행동 |
|---|---|---|---|---|
| **4건 이상** (n=16) / **3건 이상** (n=10) | **성공** | 참 비율 5%면 확률 **0.70%** | 참 비율 5%면 확률 **1.15%** | 리포트가 행동을 바꾼다 — 확정. 소스 권한·약관 정리·결제 구현을 **이 숫자를 근거로** 요구. n 을 40으로 늘려 지불의사 실측 |
| **3건** (n=16) / **2건** (n=10) | **애매** | 10%와 30%를 구분 못 함 | 동일 | **2주 1회만 연장**, n 을 두 배로. 2회 연장 금지 |
| **2건 이하** (n=16) / **1건 이하** (n=10) | **실패** | 참 비율 40%면 확률 **1.83%** | 참 비율 40%면 확률 **4.64%** | **이 제품 형태를 포기한다** (아래) |

보조 지표(판정을 뒤집지 못한다. 기록만 한다):
- 자발적 추천 발생 건수 — 1건 이상이면 성공 판정을 보강
- 지불의사 "3,900원 Yes" 비율 — 설문값이라 단독으로는 신뢰하지 않음. 단 **실가격으로 물었으므로** 성공 시 가격 결정에 바로 쓰인다
- 룰 오탐율 — 50% 초과면 성공해도 **다음 작업은 유입이 아니라 룰셋 정리**(「틀릴 조건 6」)
- 구글 계정 없음·거부로 이탈한 수 — P0-3 요구의 직접 근거

### 실패하면 무엇을 포기하는가 (구체적으로)
**Gate 3 실패**(n=16에서 2건 이하) 시 **포기 목록**. 이때는 Gate 2를 통과해 사람들이 **리포트를 끝까지 봤는데도** 행동이 바뀌지 않은 것이므로, 유입·랜딩·가격으로 변명할 수 없다:
1. **「계약서 전문을 리포트로 내주는 B2C 셀프서비스」 라는 제품 형태를 버린다.** 결제 구현·PG 계약·약관 수정·앱 출시 전부 착수하지 않는다. (번들 확인으로 결제가 **서버 엔타이틀먼트 신규 개발**임이 드러났으므로 이 포기는 아낀 비용이 더 크다.)
2. **소스·IP 이관 요구를 철회한다.** 가치 없는 자산을 받기 위해 관계 자본을 쓰지 않는다. 분사 요구를 접고 재직 상태를 유지한다.
3. **룰셋 갭 4건 보강, P0 4건 수정, 자체 도메인, SEO, 색인 등록 — 전부 폐기.**
4. 남는 선택지는 두 개뿐이고, 둘 다 **다른 아이템**이다: (i) 193룰을 중개사용 B2B 설명자료로 뒤집기 — 제품을 다시 만드는 일이므로 새 라운드 (ii) 페이퍼닥을 접고 수요가 큰 쪽(`등기부등본` 121,600 / `전입신고` 73,500)에서 새로 시작.

**실행 자체가 안 된 경우(링크 전달 7명 이하)도 실패로 기록한다.** `traction.md` 가 같은 규칙을 쓴 이유와 동일하다 — 두 달간 클릭 0의 진짜 원인이 집행 부재일 수 있고, 그렇다면 **의뢰인의 가용시간이 진짜 제약**이라는 더 중요한 사실이 확정된다. 이건 제품에 대한 결론이 아니라 **집행 능력에 대한 결론**이고, 그쪽이 더 중요하다.

## 내 명제가 틀릴 조건

아래 중 **하나라도 확인되면 상대편(`pd-thesis-own`)이 옳고, 순서를 바꿔야 한다.** 숨기지 않고 적는다.

### 1. 법무가 「약관-코드 간극을 이용한 외부인 유입」을 막으면 (가장 큰 위험, 번들 발견으로 **더 커졌다**)
약관은 "관계자에게만"이라 **공표**돼 있는데 코드는 `hasAccess = !!user` 로 전원 개방이다. `legal-ip.md` 가 「이 간극을 알면서 비관계자를 끌어오는 것은 약관 위반·근로계약상 권한 밖·회사 책임 노출」로 결론내면, 이 설계는 설계된 형태로 실행할 수 없다. 그러면 **약관·권리 정리가 먼저**이고 내 명제는 **순서에서 진다.**

이전 판(컨시어지)보다 위험이 **올라갔다**는 점을 분명히 적는다. 전에는 "관계자인 의뢰인이 직접 돌린다"는 방어선이 있었지만, 지금은 **비관계자가 직접 로그인해서 쓰는** 설계다. 코드가 열려 있다는 사실이 **의뢰인에게 권한을 주지는 않는다** — 오히려 "열려 있는 줄 알았다"는 변명을 불가능하게 만든다.
*현재 내 평가: 대표 서면 허락 없이는 금지로 결론날 확률 **60%**(이전 판 35%에서 상향). 허락이 있으면 **20%**. 그래서 Day 0 요청이 설계의 전제 조건이고, 거기에 간극을 명시하게 한 것이다.*

### 2. 대표가 16명 베타를 거절하거나 무응답이면
거절·무응답이면 막는 것은 시장이 아니라 **관계**다. 그 경우 「사용자를 만든다」보다 **권리·관계 정리가 실제 1순위**가 되고, 내 명제는 진다. 다행히 이건 **1시간 + 1~2일**에 알 수 있어, 전체 설계를 걸지 않고 확인된다. **번들 발견 때문에 이 조건은 선택이 아니라 필수 관문이 됐다.**

### 3. Gate 1 이 실패하면 (링크 수령 7명 이하)
의뢰인의 전 인맥 + 지식iN 으로 4일에 계약 예정자 8명도 못 찾는다면, **「2주 안에 실사용자를 만든다」는 1인에게 불가능**하다는 뜻이다. 그때 답은 유통 파트너(중개사·보증보험·지자체)이고, 그건 **법인 명의·약관·결제가 전제**다 — 정확히 상대편 주장이다. 내 명제가 자기 설계로 반증된다.

### 3-b. Gate 2 가 실패하면 (리포트 도달 3명 이하) — **부분 패배**
링크를 받은 사람의 80% 이상이 로그인·분석을 통과하지 못하면, 병목은 수요도 리포트 품질도 아니라 **제품의 현관**이다. 그러면 다음 작업은 **소스 권한 확보 + P0-3(카카오·이메일 로그인)·P0-1(샘플) 수정**이고, 그건 상대편 주장이다. 내 명제는 "먼저"로서만 옳고 — 2주를 들여 **무엇을 왜 고쳐야 하는지 숫자로** 넘겨주는 역할에 그친다. 그것도 두 달간 없었던 성과이긴 하나, 승리는 아니다.
*이 조건은 번들 발견으로 **새로 측정 가능해졌고**, 동시에 내가 질 수 있는 새 경로가 됐다. 구글 단독 로그인이라 통과율이 낮을 확률을 **40%** 로 본다.*

### 4. 의뢰인의 2주 가용시간이 15시간에 못 미치면
브리프는 "주간 가용시간이 적다"고만 한다. 실제 가용시간이 **주 7시간 미만**이면 n=10·관찰 3명으로 축소해야 하고(임계값은 위 표 n=10 열에 미리 계산해 뒀다), **주 3시간 미만**이면 이 설계는 집행 불가다. 그 경우 손이 가지 않아도 진행되는 작업(대표 연락 → 대기, PG 심사 → 대기)에 그 적은 시간을 쓰는 것이 합리적이고, 상대편이 옳다. **이건 내가 모르는 값이고, 메인이 의뢰인에게 확인해야 하는 단일 최대 미지수다.**
*셀프서비스 전환으로 건당 시간이 45분 → 20분으로 줄어 이 조건의 위험은 **내려갔다.***

### 5. 4주 내 외부 마감이 존재하면
예창패 2027 공고가 갑자기 뜨거나, 접수 가능한 지원사업·투자 실사·분사 합의 만료일이 4주 내에 있다면, 그 서류가 요구하는 것(사업자·IP 귀속·매출)이 순서를 강제한다. 내 근거 3이 무너지고 내 명제는 진다.
*현재 확인: 그런 마감은 **없다**(예창패 마감·2027 미공고, 공모전 창구 닫힘). 단 분사 합의가 **구두**라는 점은 만료일 없는 대신 **언제든 철회 가능**하다는 위험이기도 하다 — 이 리스크는 내 명제의 약점이고, 반론 3(b) 로 완전히 상쇄되지는 않는다.*

### 6. 룰셋 오탐율이 압도적으로 높으면 (부분 패배)
Gate 3 를 통과하더라도 발화 룰 중 사용자 인정 비율이 **50% 미만**이면, 다음 작업은 유입이 아니라 룰셋 정리다. 그건 **소스 권한이 반드시 필요한 작업**이므로, 그 시점부터 상대편 주장이 1순위가 된다. 내 명제는 "먼저"로서는 옳고 "계속"으로서는 틀린다.

## 번들 발견이 양쪽 명제에 미친 영향 (요약)

| | 내 명제(사용자 먼저) | 상대 명제(권리·결제 먼저) |
|---|---|---|
| `hasAccess = !!user` | **유리.** 「리포트를 못 본다」 반론 소멸. 컨시어지 대행 불필요 → 실제 퍼널 측정, n 12→16 | 중립 |
| 17개월 무과금 개방인데 110건 | **유리.** 「결제·관계자 제한이 막았다」는 설명 소멸 → 원인은 **노출**로 확정 | **불리.** 결제를 열어도 사용자는 안 생긴다는 뜻 |
| 결제가 `localStorage` UI 껍데기 | 중립 | **불리.** 결제 경로가 "약관 2곳+PG 심사"가 아니라 **서버 엔타이틀먼트 신규 개발** → 소스 의존 심화 |
| 약관 공표 ↔ 코드 동작 간극 | **불리.** 외부인 유입의 정당성 전제가 흔들림. 대표 서면 허락이 **선택 → 필수** 로 바뀜 (틀릴 조건 1, 확률 35%→60%) | **유리.** "권리·문서 정리가 먼저"의 실례가 하나 늘었다 |
| 구글 단독 로그인(P0-3) | **일부 불리.** 이제 변명이 아니라 측정 대상 = 내가 질 수 있는 새 경로(Gate 2, 확률 40%) | **유리.** 실패하면 소스 권한이 1순위가 된다 |

**정직하게: 이 발견은 내 명제에 유리하기만 하지 않다.** 설계 집행 가능성은 올라갔고(대행 불필요, n 증가, 실제 퍼널 측정), 정당성 전제는 내려갔다(서면 허락 없이는 진행 불가). 그래서 설계의 Day 0 이 "대표 서면 허락 + 간극 명시"로 바뀌었고, 그것 없이는 **내 명제를 집행하지 말라**고 적어 둔다.

## 요약: 왜 이게 먼저인가 (한 문단)
이 제품은 17개월간 타깃에게 **30회** 노출됐고, 그 내내 **유료 벽 없이 누구에게나 열려 있었는데**(`hasAccess = !!user`) 누적 110건이다. 0/30 은 CTR 0%와 9.5%를 구분하지 못하므로 **「별로다」는 측정된 적이 없고**, 개방 상태였으므로 **「결제가 막았다」는 설명도 불가능하다** — 남는 원인은 **노출**뿐이다. 반대편의 모든 작업(결제·소스·IP·P0)은 사용자 0을 곱하면 0이 되고, 지금 미뤄서 잃는 마감은 하나도 없으며, 그중 「제품을 먼저 고친다」는 **두 달간 실제로 실패했다**. 반면 계약을 앞둔 16명에게 **지금 완성 상태로 열려 있는 제품**의 링크를 쥐여주는 설계는 소스·결제 구현·배포 권한을 **하나도 요구하지 않고**(대표 서면 허락 1건만 요구한다), 2주 뒤에 저 네 작업 전부에 가격표를 붙여 준다. **눈을 감고 비싼 요구를 하기 전에, 거의 공짜로 눈을 뜬다.**
